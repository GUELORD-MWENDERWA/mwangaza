# Architecture technique

## 1. Choix des technologies et raisons

| Besoin | Choix | Pourquoi |
|---|---|---|
| Serveur | **Python + Django 5.2 LTS + Django REST Framework** | Tu maîtrises déjà Python et Django. Django apporte admin, migrations, authentification, sécurité, i18n. Version LTS = mises à jour de sécurité longues. |
| Base de données | **PostgreSQL 16+** | Fiable pour l'argent (transactions strictes), JSON, recherche plein texte, sécurité par ligne possible plus tard. |
| Tâches de fond | **Celery + Redis** | PDF lourds, notifications push, relances, imports Excel volumineux. |
| PDF | **WeasyPrint** | Bulletins et reçus A4 en HTML/CSS, faciles à adapter à chaque école. |
| Interface | **React + TypeScript + Vite** | Écosystème le plus riche pour une PWA hors-ligne ; Claude Code y est très efficace ; le typage évite les erreurs sur les montants. |
| Hors-ligne | **vite-plugin-pwa (Workbox) + Dexie.js (IndexedDB)** | Application installable, fichiers en cache, base locale dans le navigateur. |
| Données front | **TanStack Query** | Cache, reprise automatique. |
| Design | **Tailwind CSS + shadcn/ui** | Composants simples et accessibles, thème par école via variables CSS. |
| Formulaires | **react-hook-form + zod** | Validation identique côté formulaire et côté synchronisation. |
| Contrat API | **drf-spectacular → OpenAPI → client TypeScript généré** | Le front et le serveur ne se désynchronisent jamais. |
| Mobile | **PWA d'abord ; Capacitor en V2** pour publier sur Play Store / App Store | Un seul code ; les stores seulement quand ils apportent quelque chose (visibilité, push iPhone plus fiable). |
| Notifications | **Web Push (VAPID) via pywebpush** | Gratuit. Sur iPhone, fonctionne quand la PWA est ajoutée à l'écran d'accueil. |
| Hébergement | **1 VPS + Docker Compose + Caddy + Cloudflare** | Tient dans le budget ; Caddy gère HTTPS ; Cloudflare gère DNS, certificat wildcard et cache. |

Alternatives écartées : Laravel ou Node (tu devrais réapprendre) ; Flutter pour tout (bon en mobile mais web lourd et hors-ligne navigateur moins mûr) ; application de bureau Windows (il faudrait gérer installation et mises à jour dans chaque école, et tu veux aussi Android et iPhone).

## 2. Vue d'ensemble

```
             Cloudflare (DNS, wildcard *.mwangazaschool.com, cache)
                                  │
                         VPS ─ Caddy (HTTPS)
        ┌─────────────────────────┼─────────────────────────────┐
  {ecole}.mwangazaschool.com   parents.mwangazaschool.com     admin.mwangazaschool.com
   /app  → PWA Gestion      /  → PWA Portail            → console (V1.1)
   /api  → Django           /api/portal → Django        /api → Django
   /v/{id} → vérif reçu
        └─────────────────────────┼─────────────────────────────┘
                       Django (gunicorn) ── Celery ── Redis
                                  │
                             PostgreSQL ──► sauvegardes continues vers stockage objet
```

- L'API de l'application Gestion est servie **sur le même sous-domaine que l'école** : l'école est déduite du nom d'hôte, les cookies restent sur la bonne origine.
- Le portail parents est sur un **domaine unique**, car une famille peut avoir des enfants dans plusieurs écoles.
- Plus tard, la racine `{ecole}.mwangazaschool.com/` accueillera le site vitrine de l'école.

**Contrat de l'API** (1.6) : `make api` écrit le schéma OpenAPI (`packages/api/openapi.yaml`) puis les types TypeScript (`packages/api/src/schema.d.ts`, `openapi-typescript`) ; le client `openapi-fetch` est typé par ces types : une API changée casse la compilation du front, et la CI vérifie que les deux fichiers sont à jour. Dans le schéma, chaque champ d'une réponse est obligatoire (`apps/core/schema.py`), les corps des requêtes sont décrits à part (`COMPONENT_SPLIT_REQUEST`). Erreurs : toujours `{"code", "detail"}` ; saisie refusée : `{"code": "invalid", "detail", "fields": {"new_password": [{"code": "password_too_short", "detail"}]}}` (champ imbriqué : `contact.phone`, `permissions.0` ; erreur sans champ : `non_field_errors`) ; l'interface traduit chaque code, jamais le `detail`.

**Front de la Gestion** (1.6) : adresses en anglais sous `/app/` (`/app/login`, `…/login/code`, `…/login/new-password`, `…/login/two-factor`, `/app/account`, `/app/schools`, `/app/support`, une adresse par entrée du menu) ; dossiers par fonctionnalité (`src/features/auth`, `shell`, `account`, `schools`, `support`, `status` ; 1.7 : `settings`, `organisation`, `staff`, `roles`, `audit`). `packages/ui` : thème Tailwind 4 aux jetons des maquettes, composants façon shadcn/ui sur `radix-ui` (copiés dans le dépôt, pas un paquet), icônes des maquettes, police embarquée. `packages/i18n` : i18next, `fr` et `en` aux mêmes clés (vérifié par TypeScript et par un test), dates et heures dans le fuseau de l'école. Données de l'API avec TanStack Query ; sans réseau, un appel échoue tout de suite (« Pas de connexion au serveur ») en attendant la file d'opérations (3.4). Tests : Vitest (logique dans Node, écrans dans jsdom avec Testing Library, appareil en UTC) et Playwright (`frontend/e2e/`, parcours réels avec Django et `make demo`, job à part en CI).

## 4. Multi-écoles

**Choix : une base, un schéma, chaque ligne liée à son école.**

Pourquoi pas un schéma ou une base par école : les parents multi-écoles, les enseignants multi-écoles, les transferts d'élèves et les vues promoteur exigent des requêtes entre écoles. Avec des schémas séparés, elles deviennent compliquées et les migrations se multiplient.

Mise en œuvre :

1. `TenantModel` (abstrait, `apps/core`) : champ `school = ForeignKey(School)`, index composés commençant par `school`. Ses `save()`, `delete()` et `bulk_create()` remplissent l'école depuis l'école courante et refusent (`CrossSchoolError`) d'écrire ou de supprimer une ligne d'une autre école, de changer l'école d'une ligne (un transfert est une copie) et de relier une ligne à une ligne d'une autre école.
2. `TenantMiddleware` : lit le sous-domaine (`SCHOOL_BASE_DOMAINS` : `mwangazaschool.com` ; `localhost` en développement), charge l'école dans `request.school` et en fait l'école courante (`contextvars`) le temps de la requête, avec son fuseau horaire (`School.timezone`). École inconnue : 404 `school_not_found` ; suspendue : 403 `school_suspended`. Le domaine seul et les sous-domaines réservés (`www`, `parents`, `admin`, `api`…) n'ont pas d'école. Le rôle de l'utilisateur dans l'école est vérifié par les permissions de l'API, après l'authentification : `HasSchoolPermission` (1.2) exige une appartenance active dans l'école de l'adresse et un rôle portant le code demandé ; si les droits dans cette école exigent la double authentification, une session passée par elle (1.3). Hors requête (tâche Celery, commande, test) : `with use_school(school):`.
3. Manager par défaut `TenantManager` : filtre automatiquement sur l'école courante et **lève une erreur** (`SchoolNotSetError`) si aucune école n'est définie (évite les fuites silencieuses). Un manager `all_schools` explicite existe pour le super-admin et le portail.
4. Tests obligatoires : pour chaque endpoint, un test crée deux écoles et vérifie qu'aucune donnée de l'une n'est visible depuis l'autre.
5. **Row Level Security PostgreSQL** (S.6, `apps/core/row_security.py`), deuxième barrière si un `filter` est oublié : chaque table d'une école ne montre et ne laisse écrire, dans la base même, que les lignes des écoles de la **portée** de la connexion (`mwangaza.school_ids`, `mwangaza.all_schools`). `use_school` pose son école (requêtes d'une école, tâches Celery, commandes) ; `RowSecurityMiddleware`, après l'authentification, pose les écoles des familles du parent sur le Portail (`use_schools`) et toutes les écoles pour le super-admin dans la console et l'administration Django (`use_all_schools`), comme les tâches de la plateforme (relances, suppression d'un espace). Sans portée : aucune ligne. Règles posées après chaque `migrate`, sur **toute table d'une école** (`TenantModel` ; finance depuis S.6.1, toutes depuis S.6.2) ; hors règle, les tables sans école ou liens d'un compte avec ses écoles (`School`, `User`, `Membership`, `PushSubscription`, `PlatformAuditLog`…). Ce qui doit voir toute la plateforme entre dans `use_all_schools()` le temps de sa lecture, toujours filtré : code famille unique, identifiant déjà pris, famille cherchée par son code (activation du Portail), rôles d'un compte dans toutes ses écoles (`/me`, double authentification exigée), planificateur, purges, envoi des notifications, `make demo`. Une tâche Celery part sans portée : elle pose la sienne.

Entités **globales** (sans école) : `User`, `School`, `SchoolNetwork`, `Membership` (lien personne ↔ école), `RecoveryCode` et `LoginFailure` (codes de secours, essais de connexion ratés), `PushSubscription`, `PlatformSettings` (identité de la plateforme, une seule ligne, publique : `/api/platform/` répond à toute adresse, école suspendue ou inconnue comprise), `PlatformAuditLog` (journal de la plateforme : actions du super-admin dans la console, immuable). Entités **liées à une école** : tout le reste, y compris `Student`, `Family` et `Guardian` — chaque école a sa propre copie de l'élève et de sa famille (décision Q10 du 2026-09-26) — et `Enrollment`.

L'isolation vaut partout : application, API, exports, rapports, recherche, portail parent. Une école ne peut ni lire ni modifier les données d'une autre, et ne voit jamais qu'un élève ou une famille existe aussi ailleurs. Chaque école gère sa propre sécurité : ses comptes, ses rôles, ses permissions. Elle ne modifie un compte lui-même (noms, téléphone, mot de passe, double authentification) que s'il ne sert dans aucune autre école ; sinon, le support de la plateforme s'en charge (1.3).

**Portail parent et plusieurs écoles** (solution retenue pour Q10) : un parent a un seul compte (`User`), relié à une famille dans chaque école (`Family.primary_user`). Il relie chaque école en saisissant le code famille qu'elle lui a remis, jamais automatiquement par numéro de téléphone. L'API du portail passe par le manager `all_schools`, filtré sur les familles de ce compte : elle ne renvoie que ses enfants, chacun avec les données de son école.

## 4 bis. Espaces : réel, essai, démonstration

Décidé le 2026-10-10 (revu le même jour : au plus simple), codé par les tâches 4.15 à 4.18. **Une seule plateforme** (un serveur, une base, une console à `admin.<domaine>`) ; la console crée, lance, suspend et arrête des **espaces**. Un espace est une école (`School`) avec un type fixé à la création, jamais changé :

| Type (`School.environment`) | Contenu | Qui y entre |
|---|---|---|
| `live` — réel | vide à la création : l'école saisit ou importe ses vraies données, rien d'inventé | le personnel et les parents de l'école |
| `test` — essai | vide ; données saisies par l'utilisateur et les personnes intéressées | les comptes que la plateforme y crée |
| `demo` — démonstration | données fictives écrites par la plateforme, remises à zéro à la demande | comptes de démonstration, remis par la fiche d'accès |

- **États** (`School.status`) : `trial` (affiché « Essai gratuit »), `active` et `suspended` restent comme aujourd'hui ; `stopped` (arrêté : plus d'accès, données gardées) s'ajoute, avec un motif obligatoire gardé dans le journal de la plateforme ; un espace arrêté se relance (une erreur se rattrape, puisqu'un espace réel ne se supprime jamais). Créer un espace, c'est le lancer : pas d'état « en préparation ».
- **Pas de mélange.** L'isolation entre écoles (§ 4) sépare déjà les données. En plus : les comptes de démonstration vivent dans une plage de numéros réservée (`+243 0…` : aucun vrai numéro congolais ne commence ainsi ; ceux qu'on donne à taper sont en `+243 00…`, soit `000…` sans indicatif, car `0012…` serait lu comme un numéro international), n'ont de rôle ou de famille que dans un espace de démonstration, et ces espaces n'acceptent qu'eux (ajout de personnel, changement de numéro, activation et ajout d'une école sur le portail : `accounts.services.ensure_number_fits_space`) ; les chiffres de la console ne comptent que les espaces réels ; reçus et documents d'un espace d'essai ou de démonstration sont marqués « SPÉCIMEN ».
- **Double authentification** : pas demandée dans un espace de démonstration (comptes partagés entre visiteurs, données fictives) ; demandée comme partout dans un espace d'essai. La règle suit le type de l'espace, pas le numéro : un compte qui a aussi un rôle sensible dans un espace réel reste tenu de l'activer, et l'espace réel vérifie toujours la session à deux étapes. En développement seulement, `make demo` garde une clé commune pour le directeur, le comptable et la caissière, afin d'essayer la connexion en deux étapes.
- **Effacement** : seuls les espaces d'essai et de démonstration peuvent être supprimés, par un service unique qui parcourt tous les modèles d'une école (un nouveau modèle est couvert sans liste à tenir) ; un espace réel ne l'est jamais (on l'arrête). C'est la seule exception à la règle « paiements immuables », écrite jusque dans la base : les déclencheurs qui interdisent de modifier ou d'effacer un paiement, une clôture, un taux ou une ligne du journal d'une école laissent partir une ligne seulement si son école est un espace non réel dans l'état « suppression en cours » (`deleting`) ; rien ne se modifie jamais, et le journal de la plateforme, qui garde la trace de la suppression, reste immuable. Les comptes ne sont pas supprimés : ceux qui n'avaient que cet espace sont désactivés. Remettre une démonstration à zéro = supprimer puis recréer.
- **Démonstration depuis la console** (4.17.2, `apps/schools/demonstrations.py`) : chaque espace créé dans la console a une ligne `Demonstration` (profil petite ou grande école, bloc de numéros `+243 00 BB…` de 40 à 99, mot de passe commun chiffré, état du remplissage). La requête crée l'espace ; la tâche de fond `fill_demonstration` le remplit et note l'avancement à chaque étape. La **fiche d'accès** (adresses, mot de passe, un compte par rôle, parents du portail avec leur code famille) est un document du serveur, lu dans l'espace seulement : aperçu HTML dans la console et PDF. **Remettre à zéro** = `delete_space` puis recréation dans la transaction qui efface la ligne de l'école : même identifiant, même adresse, même bloc, nouveau mot de passe (les visiteurs d'avant n'entrent plus). Un compte d'un de ces blocs est partagé entre visiteurs : son mot de passe et sa double authentification ne changent pas (`accounts.services.ensure_not_shared`). Les espaces de `make demo` n'ont pas de ligne `Demonstration` : ni fiche ni remise à zéro dans la console.
- **Coût pour le serveur** : les espaces d'essai et de démonstration partagent la base des écoles réelles ; remplissage et suppression tournent donc en tâche de fond, par paquets, un à la fois (un seul verrou PostgreSQL pour les deux, et un refus `space_busy` plutôt qu'une file d'attente), et le nombre d'espaces de démonstration est limité par un réglage (`DEMO_SPACES_MAX`, 5 par défaut). Le type n'ajoute rien à la synchronisation des appareils.
- **Pas de passage d'un type à l'autre** : une école qui a essayé repart d'un espace réel vide.
- `make demo` reste l'outil du développement (réglage `DEMO_DATA`) et utilise le même code que la console (`apps/core/demo.py` : `fill(spaces, on_step)`, une liste d'étapes, une transaction par étape ; chaque étape reçoit des `DemoSpace` — école, profil des données d'exemple, numéros, mot de passe — et ne touche à rien d'autre sur la plateforme) ; `itig` et `volcans` sont des espaces de démonstration ; hors développement (`DEBUG`), aucun super-admin de démonstration n'est créé, et celui d'un ancien `make demo` perd ses droits. Depuis la 4.22, la commande refuse avant toute écriture dès qu'un espace réel existe, quel que soit le réglage, et ne change jamais le type d'un espace (code `itig` ou `volcans` pris par un espace d'un autre type : refus) ; sur une plateforme qui a de vraies écoles, les démonstrations se créent dans la console.

Écartée : un serveur par type (trois bases, trois consoles) — plus cher, trois mises à jour à chaque version, et contraire à la console unique.

## 5. Hors-ligne et synchronisation

### 5.1 Ce qui marche hors-ligne en V1.0

Consultation des élèves et de leur situation financière, encaissement, impression et réimpression des reçus, demande d'annulation (validée en ligne), clôture de caisse (envoyée à la reconnexion).

### 5.2 Principes

1. **Chaque appareil est enregistré** (`Device`) lors de la première connexion en ligne, rattaché à une école et, pour la caisse, à une `CashRegister`. Il reçoit un préfixe court (ex : `C1`).
2. **Identifiants UUID v7** générés sur l'appareil pour tout ce qui est créé hors-ligne.
3. **Numéro de reçu unique sans serveur** : `{CODE_ECOLE}-{PREFIXE_APPAREIL}-{AA}-{séquence locale}`, ex : `ITIG-C1-26-000184`. La séquence est stockée dans IndexedDB et sauvegardée côté serveur à chaque synchronisation pour être restaurée si l'appareil est réinstallé.
4. **Journal d'opérations (outbox)** : chaque action hors-ligne écrit une opération dans une file locale `{op_id, type, payload, created_at, device_id}`. Les opérations sont envoyées dans l'ordre, par lots.
5. **Idempotence** : le serveur garde `op_id` ; une opération reçue deux fois n'est appliquée qu'une fois et renvoie le même résultat.
6. **Pas de conflit sur l'argent** : un paiement est une écriture ajoutée, jamais modifiée. Deux caissiers hors-ligne qui encaissent pour le même élève créent deux paiements valides ; le solde est recalculé à partir de tous les paiements.
7. **Surpaiement** : si, après synchronisation, un élève a payé plus que dû (deux caisses hors-ligne), le surplus devient un **crédit** sur l'élève, signalé au comptable. Jamais de rejet d'un paiement déjà encaissé physiquement.
8. **Données modifiables** (fiche élève) : « dernière écriture gagne » champ par champ, avec historique dans l'audit ; conflit signalé si deux modifications touchent le même champ dans la même fenêtre.
9. **Descente des données (pull)** : le serveur tient un `ChangeLog` par école avec un numéro croissant. L'appareil demande « tout depuis le numéro N » et met à jour sa base locale. Premier chargement : instantané complet de l'école (élèves, classes, frais, échéances, soldes), compressé.
10. **Configuration en ligne seulement** : frais, barèmes, rôles, classes. Hors-ligne, l'appareil utilise la dernière version reçue.

### 5.3 Endpoints

- `POST /api/sync/push/` — lot d'opérations (100 au plus) et dernier numéro de reçu de l'appareil ; réponse : statut par `op_id` (`applied` / `duplicate` / `rejected` + erreur).
- `GET /api/sync/pull/?since={seq}&limit=…` — changements depuis `seq`, avec l'état actuel de chaque entité ; `snapshot_required` si `since` dépasse le dernier numéro.
- `GET /api/sync/snapshot/?after=…&limit=…` — instantané initial par pages d'inscriptions ; la première donne le curseur, l'appareil (séquence de ses reçus) et la configuration. Compression : par Caddy (4.6).
- Seulement depuis l'appareil enregistré de la session (`device_required`, `device_revoked`), avec `students.view` ou `finance.collect_payment` ; frais et paiements selon les droits finance.

### 5.4 Côté navigateur

- Demander le stockage persistant (`navigator.storage.persist()`), afficher un avertissement si refusé.
- Indicateur permanent : en ligne / hors-ligne / opérations en attente / dernière synchronisation.
- Synchronisation au retour du réseau, au démarrage, et toutes les 60 s en ligne.
- Mise à jour de l'application : nouvelle version proposée, jamais forcée pendant qu'il reste des opérations non envoyées. Service worker de Workbox (`vite-plugin-pwa`, seulement après `make build`) enregistré par l'application elle-même (`UpdatePrompt.tsx`, sans `workbox-window`) ; nouvelle version cherchée au démarrage et toutes les heures, installée quand la personne clique « Mettre à jour ».
- Navigateurs recommandés pour la Gestion : Chrome ou Edge récents.

### 5.5 Authentification hors-ligne

- Connexion complète exigée en ligne au moins une fois par appareil, puis au moins une fois tous les 7 jours (configurable).
- Le PIN déverrouille les données locales ; il est vérifié contre une empreinte stockée localement (PBKDF2). Limite connue : un appareil volé déverrouillé expose les données en cache ; d'où l'expiration, la révocation d'appareil par l'admin et l'effacement local à la révocation.

## 6. Argent

- Montants en entiers dans la plus petite unité : `amount_minor` + `currency` (ISO : `USD`, `CDF`).
- Package `money` partagé côté front ; côté Python, une classe `Money` immuable.
- Devise : choisie pour chaque barème (`FeeRule.currency`), USD ou FC.
- Taux : `ExchangeRate(school, academic_year, USD → CDF, rate)`, fixe pour l'année scolaire, saisi par le comptable ; une correction en cours d'année ajoute une ligne (historique : qui, quand, ancien et nouveau taux) et ne change pas les paiements passés.
- Conversion : le paiement enregistre `rate_used` (toujours dans le sens USD → CDF) et le montant dans la devise du frais. FC → USD = division en `Decimal` par le taux ; arrondi demi supérieur à l'unité de la devise (centime, franc).
- Solde d'un élève = somme des montants dus (barèmes − réductions) − somme des paiements non annulés, par devise de frais. Calculé à la demande et mis en cache ; recalculable à tout moment.

## 7. Impression

- **Format du reçu choisi par l'école** (paramètres, `04` § 1) : thermique 58 mm ou 80 mm, ou imprimante ordinaire sur une feuille de la largeur d'un A4, demi (21 × 14,8 cm) ou tiers (21 × 9,9 cm), un reçu par feuille, un seul exemplaire (DOC.2).
- **Reçu thermique** : page HTML dédiée avec CSS `@page { size: 58mm auto; margin: 0 }` ou `80mm auto`, imprimée par la boîte de dialogue du navigateur (fonctionne hors-ligne). Configurer une fois l'imprimante par défaut sur le poste. Logo : version noir et blanc de l'école, sinon logo en niveaux de gris. Plus tard si besoin : impression directe ESC/POS via Web Serial / WebUSB. Le modèle exact de l'imprimante ne bloque rien : chaque école choisit son format.
- **A4** : même principe hors-ligne ; PDF serveur (WeasyPrint) pour les documents générés en ligne (listes, situations, fiches).
- **QR code** généré dans le navigateur ; il pointe vers `https://{ecole}.mwangazaschool.com/v/{payment_id}`, suivi, sur un appareil mémorisé, du contenu du reçu signé par l'appareil : `?n=` numéro, `t=` heure en secondes, `a=` montant, `c=` devise, `r=` caisse, `s=` signature de `id|n|t|a|c|r` (3.5.2).
- **Vérification d'un reçu imprimé hors ligne** : à son enregistrement (3.3), l'appareil crée une paire de clés ECDSA P-256 avec WebCrypto ; la clé privée, non exportable, reste dans le navigateur (IndexedDB) ; la clé publique est enregistrée sur `Device.public_key`. Chaque reçu est signé sur l'appareil. La page `/v/…` affiche le minimum (école, numéro, date, montant, élève en initiales, valide / annulé) : pour un paiement déjà synchronisé, elle lit la base et refuse un QR dont le contenu diffère ; pour un paiement pas encore reçu, elle vérifie la signature et affiche « reçu authentique, émis hors ligne par la caisse C1, en attente de synchronisation ». Un appareil révoqué ne produit plus de reçu valide. La signature n'ajoute aucune dépendance (WebCrypto est dans tous les navigateurs récents) ; le dessin du QR code en demandera une, à valider en 3.2.

## 8. Sécurité

- Sessions Django en cookie `HttpOnly`, `Secure`, `SameSite=Lax`, protection CSRF (vérifiée aussi sur les étapes de connexion, avant qu'un compte soit connecté ; `GET /api/auth/csrf/` donne le cookie ; Django en change la valeur à la connexion : l'application la relit).
- **Connexion en plusieurs étapes** (`apps/accounts/login.py`) : mot de passe → code de double authentification si elle est activée → nouveau mot de passe si le mot de passe est provisoire → activation de la double authentification si un rôle l'exige. Le compte n'est connecté qu'après toutes ses étapes ; avant, la session ne garde que la connexion en cours (10 minutes).
- Mots de passe : Argon2 (`argon2-cffi`) ; un ancien hachage PBKDF2 est converti à la connexion suivante. Au moins 10 caractères, ni trop proche du numéro ou des noms, ni trop courant, ni seulement des chiffres.
- **Limitation des tentatives** (`apps/accounts/attempts.py`, sans dépendance) : 5 essais ratés pour un numéro en 15 minutes → numéro bloqué 15 minutes, même sans compte ; 30 d'une même adresse IP → adresse bloquée 15 minutes. Mot de passe (API et administration Django, par le moteur d'authentification), code de double authentification ou de secours, mot de passe actuel. Réponse `429 too_many_attempts` + `Retry-After`. Adresse IP réelle (4.6.1) : Caddy ne croit `CF-Connecting-IP` que d'une requête venue de Cloudflare et l'écrit dans `X-Real-IP` ; Django ne lit cet en-tête qu'en production (`CLIENT_IP_HEADER`), adresse vérifiée, sinon l'adresse de connexion (`apps/core/http.py`).
- **Double authentification TOTP** (RFC 6238, `apps/accounts/totp.py`, sans dépendance) obligatoire pour qui a un droit sur l'argent, les réglages, les comptes ou l'audit (par défaut : directeur, comptable, caissier, promoteur ; `04` § 8). Clé chiffrée en base (`cryptography`, clé dérivée de `DJANGO_SECRET_KEY`, anciennes clés dans `DJANGO_SECRET_KEY_FALLBACKS`) ; un code ne sert qu'une fois ; 8 codes de secours à usage unique, gardés en empreinte HMAC ; « ne plus demander sur cet appareil pendant 7 jours » par un cookie signé, annulé par un changement de mot de passe ou de clé. **Changer `DJANGO_SECRET_KEY` sans garder l'ancienne dans `DJANGO_SECRET_KEY_FALLBACKS` oblige chacun à réactiver sa double authentification.** Super-admin : toujours exigée ; l'administration Django (`apps/accounts/admin_site.py`) a sa propre connexion en étapes, avec les mêmes fonctions et la même limitation des tentatives (jamais d'« appareil de confiance »), et ne s'ouvre qu'à une session passée par la double authentification.
- Permissions vérifiées côté serveur ; les rôles portent des codes de permission (`finance.collect_payment`, `finance.request_cancellation`, `finance.close_register`, `students.import`… : liste dans `04` § 8).
- **Journal d'audit** (`apps/audit`, `AuditLog`) : qui, quoi, sur quoi, quand, école, adresse IP, navigateur, avant / après (seulement les champs changés), super-admin en session support (`impersonated_by`) ; appareil de caisse en 3.3. Écrit par `apps.audit.services.record()` **dans la transaction de l'action** (action annulée = pas d'entrée). **Ni modifiable ni effaçable** : refusé par le modèle et par un déclencheur PostgreSQL (`UPDATE` et `DELETE` refusés même en SQL direct). **Jamais de secret** : `record()` refuse les clés `password`, `totp_secret`, `recovery_codes`… ; une action sur un mot de passe ou une double authentification est notée sans valeur. Où va une entrée : ce qui se passe dans une école (rôles, personnel, connexion à son adresse) va dans son journal ; ce qui change un compte (mot de passe, double authentification, par la personne ou par le support) va dans le journal de **chaque école où la personne est active**, sans dire où l'action a été faite. Lecture : `GET /api/audit/` (`audit.view`, filtres personne, action, domaine, objet, dates, recherche) ; administration Django en lecture seule. Liste des actions : `apps/audit/actions.py`.
- **Session support « en tant qu'école »** (A3, `apps/accounts/support.py`) : le super-admin se connecte à l'adresse de l'école comme tout le monde (mot de passe et code), puis ouvre la session avec un motif (`POST /api/support/`). Une heure au plus ; droits de l'école sauf la caisse (encaisser, demander ou valider une annulation, clôturer) ; gardée dans la session de cette adresse seulement ; refusée dans une école suspendue. Ouverture (motif, heure de fin), fermeture (bouton ou déconnexion) et chaque action de la session vont dans le journal de l'école avec `impersonated_by` ; l'école y lit « Support Mwangaza ». `/api/me/` renvoie la session pour le bandeau rouge de l'interface.
- **Compte super-admin** (S.3.1, `apps/accounts/privileged.py`), où qu'il soit utilisé (console, administration Django, adresse d'une école) : session fermée après **2 heures sans activité** (réécrite au plus toutes les 5 minutes) ; réglage facultatif du serveur `DJANGO_CONSOLE_ALLOWED_IPS` (adresses ou réseaux, vide = toutes) : hors liste, la connexion répond comme un mauvais mot de passe et une session ouverte reçoit 403 `address_not_allowed` ; une entrée mal écrite n'autorise personne. Chaque connexion, chaque code refusé et chaque refus d'adresse est au journal de la plateforme (`access.*`, avec l'adresse IP et le site) et, comme chaque session support ouverte, **montré sur l'écran des super-admin abonnés dans la console** (S.3.2, `apps/notifications/console.py` : Web Push par Celery, celui qui agit compris, console fermée et déconnecté compris ; pas de ligne `Notification`, l'alerte renvoie au journal ; file de tâches injoignable : l'alerte est perdue et notée, jamais la connexion du super-admin). Le service worker de la console (`public/push-sw.js`) ne fait que cela : aucun cache. Adresse d'un abonnement Web Push : `https` seulement, pour les trois applications (le serveur n'écrit jamais à un service interne).
- **Droits sensibles** (S.3.1) : quand un compte reçoit `roles.manage` ou un droit `finance.*` (rôle donné, compte réactivé, rôle élargi), ceux qui gèrent les rôles de l'école reçoivent la notification `sensitive_rights`, auteur compris et sauf l'intéressé ; elle ne se coupe pas dans les préférences.
- **Fichiers envoyés** (S.4) : liste blanche, jamais un filtre de ce qui est interdit. **Images** (logo et logo noir et blanc de l'école, photo d'élève, logo et icône de la plateforme) : PNG ou JPEG, 1 Mo et 2 048 px de côté au plus (dimensions lues dans l'en-tête avant de décoder), puis **ré-encodées** par `apps/core/images.py` (Pillow, décodeurs PNG et JPEG seuls) : ce qui est enregistré est une image neuve faite des seuls pixels — ni EXIF, ni position GPS, ni octets cachés ; l'orientation de l'appareil est appliquée avant. **SVG** : refusé pour une école (ceux d'avant restent servis) ; permis pour le logo de la plateforme, envoyé par le super-admin, sans script, gestionnaire d'événement ni entité XML. Logos et icône servis avec `nosniff` et une politique `sandbox` qui empêche tout script, même ouverts seuls. **Pièce jointe d'une annonce** : PDF reconnu à ses premiers octets, 5 Mo, servi en `attachment` (jamais ouvert dans une page à l'adresse de l'application). **Imports** : Excel ou CSV, 5 Mo, 5 000 lignes, lus en flux. **Toute requête** : 10 Mo au plus, refusée par Caddy (413) avant Django (`infra/routes.caddy`). Administration Django (dépannage, super-admin) : mêmes refus, sans ré-encodage.
- Alertes : plus de N annulations par jour pour un caissier, écart de caisse au-dessus d'un seuil, connexion « en tant qu'école » par le super-admin.
- Secrets dans des variables d'environnement, jamais dans le dépôt.
- Dépendances surveillées (S.2) : Dependabot (`.github/dependabot.yml`, uv, pnpm, Docker, Actions, groupé chaque lundi, **sans les versions majeures** ni un autre Python dans l'image : chacune est une décision à part) ; `.github/workflows/audit.yml` : `pip-audit` (lancé par `uvx`, hors des dépendances du projet) et `pnpm audit --prod --audit-level high`, sur `main`, chaque lundi et sur une PR qui change un verrou (pas sur les autres : une faille nouvelle ne bloque pas un travail sans rapport). Secret scanning et push protection de GitHub (réglage 👤).
- **Compte PostgreSQL de l'application** (S.5, `apps/core/db_roles.py`) : en production, Django et Celery se connectent avec `mwangaza_app`, qui n'est ni superutilisateur ni propriétaire des tables. Il lit et écrit des lignes (`SELECT`, `INSERT`, `UPDATE`, `DELETE`), rien d'autre : pas de `TRUNCATE`, pas de déclencheur désactivé ou remplacé, pas de table créée ou supprimée, pas de `session_replication_role`. Les déclencheurs d'immuabilité (paiements, répartitions, annulations, crédits, clôtures, taux, deux journaux) ne se contournent donc plus depuis l'application, même par une requête SQL glissée. Les migrations passent par le compte propriétaire `mwangaza`, dans le conteneur `migrate`, seul à connaître son mot de passe ; il lance ensuite `manage.py setup_app_role` (compte créé ou remis d'aplomb, mot de passe envoyé haché, droits des tables d'aujourd'hui et de demain). **Tout changement de structure passe par une migration**, jamais par un service. Développement et tests : un seul compte.
- **Renforcement prévu (bloc S, `05` § 4 bis)** : en-têtes et CSP des trois applications (faits, S.1), Cloudflare en proxy avec pare-feu limité à Cloudflare (S.1) ; secrets surveillés (faits, S.2) ; comptes à privilèges : journal, session courte, adresses autorisées, alerte de l'école (faits, S.3.1), alertes push au super-admin (faites, S.3.2) ; logos des écoles en PNG / JPEG seulement, images ré-encodées (faits, S.4) ; compte PostgreSQL à droits minimaux, paiements non effaçables par la base (faits, S.5) ; Row Level Security (faite, S.6.1 et S.6.2) ; protection des données, détection, revue OWASP ASVS niveau 2 (S.7 à S.9).
- **IA (V1.4, `05` § 6.5)** : appels à Claude depuis le serveur seulement ; outils en lecture seule qui passent par les services avec les permissions de la personne ; minimisation (ni téléphones, ni photos, ni adresses) ; toute action proposée passe par l'écran normal, avec confirmation et audit ; **pilotée par la console** : usages déclarés (`ai/uses.py`) affectés à chaque école, crédits du mois, plafond de la plateforme, cinq verrous avant chaque appel (`ai.services.authorize`), un seul fichier qui parle à l'API, appels en tâche de fond (file `ai`), registre `AiCall` sans le texte des échanges et cumul mensuel `AiUsageMonth`.

## 10. Carte unique et présences (V1.5) — aperçu

- **Une carte** par élève et par membre du personnel : puce **NTAG215 / 216** (NFC Forum type 2, lue par tous les téléphones Android NFC et par les modules PN532 / RC522 ; les cartes MIFARE Classic, illisibles par beaucoup de téléphones, sont écartées) + QR code imprimé + photo. La puce et le QR portent le **même jeton secret** (pas le matricule), révocable en cas de perte ; la puce est protégée en écriture après l'encodage.
- **Liaison** sur un appareil enregistré (`Device`) : scanner le QR imprimé puis poser la carte → le jeton est écrit dans la puce et son numéro de série noté ; refus d'une carte déjà liée ou d'une autre école.
- **Pointage de deux façons** : puce lue par un téléphone Android enregistré (Web NFC de Chrome : lecture du numéro de série et du contenu, écriture ; pas sur iPhone) ou par un lecteur **ESP32** (PN532 + écran + buzzer, `Device` de type `reader`, jeton propre à l'école) ; QR lu par la caméra de n'importe quel appareil enregistré, iPhone compris.
- Pointages `{card_token, timestamp, device}` envoyés au serveur ; hors ligne : gardés sur l'appareil (file d'opérations) ou en mémoire flash de l'ESP32, renvoyés ensuite (idempotence par identifiant de pointage).
