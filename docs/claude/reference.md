# Référence — commandes en détail et adresses en développement

Sorti de `CLAUDE.md` le 2026-10-04 : `CLAUDE.md` est lu à chaque conversation, il doit rester court. Ici, le détail, à lire au besoin (`grep -n`) et **à tenir à jour dans la PR de chaque tâche** qui ajoute un écran, une API, une commande ou des données à `make demo`. Version pour l'utilisateur, en langage simple : `A-FAIRE.md` § 11.

## Commandes en détail

| Commande | Effet |
|---|---|
| `make dev-local` | Django et Vite sur la machine (valeurs dans `.env`, copié de `.env.example`) ; recette en bash pour que Ctrl+C arrête proprement les quatre serveurs ; Vite lancé app par app (`pnpm dev` afficherait un faux échec à l'arrêt) |
| `make services` | seulement PostgreSQL et Redis dans Docker, prêts (`--wait`) ; rarement utile : la cible cachée `db-up` les démarre avant `dev-local`, `migrate`, `makemigrations`, `demo`, `superuser`, `shell` et `test-back` (pas en CI, où `CI` est défini) |
| `make reset-db` | efface la base de développement de Docker (et celle des tests : `down --volumes`), puis `make migrate demo` ; pour une base qu'une migration ne peut plus suivre (`InconsistentMigrationHistory`, ex. nouveau modèle de compte en 1.2) |
| `make demo` | crée ou remet à jour les données fictives (`apps/core/management/commands/demo.py`) : identité de la plateforme de départ (nom, couleurs, sans logo ni icône) avec un support et des mentions légales fictifs ; écoles `itig` et `volcans` (espaces réels jusqu'à la 4.17, puis de démonstration), un compte par rôle (`apps/accounts/demo.py` : téléphones `0000001001`…, super-admin `0000000000`, mot de passe `mwangaza-demo` ; double authentification activée avec une clé commune pour les comptes qui l'exigent, super-admin compris, sauf le promoteur de l'ITIG) ; remet les écoles de démonstration comme au départ (couleur, abonnement, pas suspendues, logo public de l'ITIG) et leur organisation scolaire (année 2026-2027 en cours, découpage, niveaux, options, classes, format du matricule) ; frais de l'année (grille fictive : types, barèmes, tranches) et taux s'il manque ; élèves (800 à l'ITIG, 150 aux Volcans, avec familles et inscriptions ; créés une seule fois par école) ; réductions, caisses (toutes fermées) et paiements depuis la rentrée, deux crédits d'élèves et des demandes d'annulation (validée, refusée, en attente) par école ; un appareil par caissier et secrétaire ; trois annonces par école (une archivée, lues par une famille sur deux) ; trois annonces de la plateforme (toutes les écoles, ITIG seule, une archivée), remises à « non lues », avec leurs notifications au personnel des écoles visées (aussi remises à « non lues ») ; compte du portail (`0002000001`) relié à la famille des deux écoles côté ITIG, code des Volcans affiché pour « Ajouter un enfant d'une autre école » ; trois demandes de coordonnées des parents à l'ITIG ; environ une famille sur trois a activé son compte du portail (une seule fois par école) ; débloque les essais ratés ; refusé hors développement, essai sur plusieurs appareils et serveur de démonstration (réglage `DEMO_DATA`) ; avec le réglage `DEMO_PASSWORD` (serveur de démonstration, `DJANGO_DEMO_PASSWORD`) : ce mot de passe au lieu de `mwangaza-demo`, et aucune clé commune de double authentification (retirée si présente ; une clé liée par la personne est gardée) ; un mot de passe déjà le bon n'est pas réécrit : les sessions ouvertes restent ouvertes |
| `make messages` | traductions du serveur : `makemessages -l fr` puis `compilemessages` (`backend/locale/fr/LC_MESSAGES/django.po` et `.mo`, les deux dans Git) ; demande gettext ; texte source en anglais, **tout** texte traduit en français dans la même PR (`apps/core/tests/test_translations.py` refuse un texte vide ou « fuzzy » et un `.mo` pas recompilé) ; le serveur répond dans la langue de l'interface (cookie `django_language` posé par `packages/i18n`) |
| `make test` · `make test-back` · `make test-front` | pytest ; vérification des types puis Vitest (`*.test.ts` : logique, dans Node ; `*.test.tsx` : écrans, navigateur simulé jsdom avec Testing Library ; appareil en UTC), dans `frontend/apps` et `frontend/packages` |
| `make test-e2e` | parcours dans Chromium (Playwright, `frontend/e2e/`) : Django + Gestion aux adresses des écoles + console (`admin.localhost:5175`), données remises à zéro par `make demo` avant et après ; réutilise des serveurs déjà lancés (`make dev-local`) ; une fois avant : `cd frontend && pnpm exec playwright install chromium` |
| `make guide` | guide de la version en PDF (`docs/guide/guide-v<version>.pdf`, dans Git) : `frontend/guide/` — config Playwright à part (Django, Gestion, Portail ; `make demo` avant et après), `captures.spec.ts` (connexion avec chaque compte de démo, captures JPEG dans `guide/captures/`, hors Git ; version et nom de la plateforme), `guide.html` (texte, jetons du design) imprimé par Chromium ; pas dans la CI ; à la fin de chaque version : texte mis à jour, puis `make guide` |
| `make prod-local` · `make prod-local-stop` | essai de la production sur la machine (`infra/docker-compose.yml`, valeurs de `infra/local.env`, projet `mwangaza-essai`) : images construites depuis `infra/Dockerfile` (front construit, Django + gunicorn, Caddy `tls internal`), ports 80 et 443 ; base vide (`make demo` refusé : pas de `DEMO_DATA`) ; arrêt sans effacer les données ; les deux essais ne voient pas les variables du `.env` de développement |
| `make reseau` · `make reseau-demo` · `make reseau-ip` · `make reseau-stop` | essai de l'application construite sur plusieurs appareils du même réseau (tâche 4.11, pas à pas : `A-FAIRE.md` § 9 bis) : `infra/docker-compose.yml` + `infra/docker-compose.reseau.yml`, projet `mwangaza-reseau` (données à part), valeurs de `infra/reseau/reseau.env` (hors Git, créé avec des secrets neufs par `infra/reseau/essai.py init`) ; adresse DuckDNS mise à jour vers l'adresse de la machine (`essai.py ip`), page des QR codes (`essai.py accueil`) ; Caddy avec le module `caddy-dns/duckdns` (`Caddyfile.reseau`, routes communes dans `infra/routes.caddy`) : un seul certificat Let's Encrypt joker par DNS ; `reseau-demo` : `make demo` dans l'essai (`DJANGO_DEMO_DATA`) ; codes : `make totp` |
| GitHub Actions (`.github/workflows/ci.yml`) | à chaque PR et sur `main` : `make lint-back test-back` + schéma OpenAPI à jour (PostgreSQL 16) ; types du client de l'API à jour + `make lint-front test-front build` ; `make test-e2e` (job à part, PostgreSQL + Chromium). Sur une PR, le job « Fichiers changés » (`.github/scripts/changes.sh`, essayable sur la machine : `printf 'docs/06-suivi.md\n' \| .github/scripts/changes.sh`) choisit les jobs à lancer : `docs/`, `maquettes/`, `.claude/`, `*.md` hors `backend/` et `frontend/` → aucun ; `frontend/` → front + parcours ; `backend/` et `docs/ecole-pilote/` (logo lu par `make demo`) → serveur + parcours ; `frontend/packages/api/openapi.yaml` et tout autre fichier (Makefile, `infra/`, `.github/`) → tout. Un job sauté s'affiche « Skipped ». Sur `main`, tout est relancé après chaque fusion |
| `make deploy-setup` · `make deploy` · `make deploy-demo` · `make deploy-superuser` · `make deploy-logs` · `make deploy-ssh` | serveur de démonstration en ligne (tâche 4.6.2, pas à pas : `A-FAIRE.md` § 9 ter, skill `/deployer`) : VM Oracle Cloud « Always Free » (ARM) + adresse DuckDNS, piloté par SSH depuis la machine (`infra/serveur/deployer.sh`) ; valeurs de `infra/serveur/serveur.env` (hors Git, créé avec des secrets neufs par `essai.py --serveur init`, copié sur le serveur à chaque mise en ligne, **à garder en lieu sûr**) ; `deploy-setup` une fois (`preparer.sh` en root : mises à jour automatiques, Docker, ports 80/443, SSH par clé) ; `deploy` : DuckDNS vers l'IP publique (fin de `SERVEUR`), page des QR codes, `git archive origin/main` (ou `ref=`) envoyé par SSH dans `~/mwangaza/code` (mise à jour sur place par `rsync`), images construites sur le serveur puis `up --wait` (projet `mwangaza`) ; même configuration que `make reseau` (`docker-compose.reseau.yml`) avec `DJANGO_DEMO_PASSWORD` : `deploy-demo` met ce mot de passe, sans clé commune de double authentification (chacun lie son application à la 1re connexion et la garde) ; `deploy-logs service=django` |

## Adresses en développement

- **Gestion** `http://itig.localhost:5173/app/` (le sous-domaine = code de l'école ; `…/api/school/` renvoie l'école ; écrans : `/app/login` et ses étapes `…/code`, `…/new-password`, `…/two-factor`, `/app/account`, `/app/schools`, `/app/support`, `/app/students/invitations` (invitations au portail), `/app/platform-news` (annonces de la plateforme ; bandeau de la dernière non lue en haut de chaque écran, lien en bas du menu), `/app/notifications` (centre de notifications, ouvert par la cloche de la barre du haut ; activer les notifications sur l'écran de cet appareil, essai, sortes à recevoir ; réception seulement avec le service worker, donc après `make build` et `pnpm preview`), une adresse par entrée du menu, guide du caissier et du comptable par-dessus les écrans (« Aide et guide » en bas du menu) ; service worker seulement après `make build`, essai avec `cd frontend/apps/gestion && pnpm preview` sur le port 4173)
- **Portail** `http://localhost:5174/` (écrans `/login`, `/activate` (code famille prérempli depuis `#<code>`, QR de la lettre d'invitation), `/forgot-password`, `/` (mes enfants), `/children/<id>` (paiements), `/announcements`, `/profile`, `/add-school`, `/install`, `/guide` (guide du parent, après l'activation) ; service worker seulement après `make build` ; API sans école `/api/portal/auth/login/` · `activate/` · `reset/`, `/api/portal/me/`, `/api/portal/profile/`, `/api/portal/families/` · `families/link/`, `/api/portal/children/<id>/` · `…/photo/`, `/api/portal/payments/<id>/receipt/`, `/api/portal/announcements/` · `read/`, refusée à l'adresse d'une école ; session : 90 jours après la dernière visite avec « Rester connecté » (prolongée par `/api/portal/me/`, une écriture par jour au plus), sinon 12 heures ; `localStorage` `mwangaza.portal.lastSession` : trace d'une session ouverte, pour remplir le numéro et ramener à la page demandée après une session finie, effacée à la déconnexion)
- **Console de la plateforme** `http://admin.localhost:5175/` (super-admin seulement : à cette adresse, `/api/auth/login/` refuse tout autre compte et demande toujours le code ; écrans `/login`, `/login/code`, `/login/finish` (première connexion terminée dans l'administration, même session), `/` tableau de bord, `/identity` identité de la plateforme, `/schools` écoles · `/schools/new` · `/schools/<id>`, `/accounts` comptes · `/accounts/<id>`, `/announcements` annonces aux écoles, `/devices` appareils, `/journal` journal de la plateforme · `/journal/support` sessions support ; API `/api/console/dashboard/`, `/api/console/platform/` · `logo/` · `icon/` (identité modifiable, chaque changement au journal de la plateforme), `/api/console/schools/` · `<id>/` · `<id>/suspend/` · `<id>/stop/` · `<id>/reactivate/` (liste filtrée par `?environment=live|test|demo` et `?status=`, création avec le directeur et le type d'espace, noms, adresse et abonnement, arrêt avec motif ; au journal de la plateforme), `/api/console/accounts/` · `<id>/` · `<id>/new-password/` · `<id>/reset-totp/` (comptes de toutes les écoles : recherche, noms, téléphone, accès ; au journal de la plateforme et des écoles), `/api/console/announcements/` · `<id>/archive/` (annonces aux écoles : liste avec « lue par N », publication, archivage ; au journal de la plateforme), `/api/console/devices/` · `<id>/revoke/` (appareils de toutes les écoles ; déconnexion au journal de l'école et de la plateforme), `/api/console/support-sessions/` (sessions support reconstituées depuis le journal des écoles), `/api/console/audit/` (journal de la plateforme, filtres), introuvables ailleurs)
